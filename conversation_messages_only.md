# Product concept: 10-Minute Programmer Test

The test should answer:

> **“Can this person actually read code, reason about a problem, identify edge cases, and produce a working solution under pressure?”**

Not:

> “Does this person remember obscure syntax?”

I'd structure the first test around **3 layers**.

---

## Test structure

**Total: 10 minutes**

| Section | Time | What it measures |
|---|---:|---|
| 1. Debug the code | 2 min | Reading + debugging |
| 2. Solve the problem | 5 min | Actual coding ability |
| 3. Reason about the solution | 3 min | Problem solving + engineering judgment |

The candidate should not know exactly which type of problem is coming next.

---

# Question 1 — “Find the Bug”

### Difficulty: Easy → Medium
### Time: 2 minutes

Give them a small piece of code.

Example:

```javascript
function countUnique(items) {
  const seen = {};

  for (const item of items) {
    seen[item] = true;
  }

  return seen.length;
}
```

### Question

> This function is supposed to return the number of unique items.
>
> Example:
>
> `["a", "b", "a", "c"] → 3`
>
> Identify the bug and provide the corrected implementation.

Expected realization:

```javascript
return Object.keys(seen).length;
```

But **don't make the scoring simply “did they type the expected line.”**

We can evaluate:

- Did they identify the actual problem?
- Did they understand why `seen.length` is undefined?
- Did their solution handle the input correctly?
- Did they introduce another bug?

### Why this is useful

A surprisingly large percentage of weak programmers can write code but struggle to **read and reason about existing code**.

That's a real engineering skill.

# Question 2 — “The Real Coding Test”

This should be the centerpiece.

### Difficulty: Medium
### Time: 5 minutes

> If no such character exists, return `null`.

Examples:

```text

"aabbcc"    → null
"leetcode"  → "l"
"program"   → "p"
""          → null
```

Function:

```javascript

  // your code
}
```

### Why I like this question

It's deceptively simple.

- frequency counting
- preserving order
- empty input
- no unique characters
- time complexity

A strong solution is approximately:


where `k` is the number of distinct characters.

But importantly:

**Don't show them the complexity requirement.**

We want to observe whether they naturally produce a reasonable solution.
